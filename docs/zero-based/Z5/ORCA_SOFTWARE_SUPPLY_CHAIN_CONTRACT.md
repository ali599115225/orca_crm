## 1. Purpose

Define the controls required to trust source, dependencies, build inputs, artifacts, and release evidence. This contract does not authorize deployment or claim SLSA attainment.

## 2. Source control

- protected central and release branches;
- pull requests for material changes;
- required status checks cannot be bypassed silently;
- CODEOWNERS/review policy selected by risk area;
- signed/verified identity where practical;
- no direct Production change from an unreviewed local state;
- force push and history rewrite prohibited on protected branches;
- secrets, credentials, private keys and sensitive exports prohibited in history.

## 3. Dependency policy

| Control | Target |
|---|---|
| Lockfile | committed and generated by approved package manager/runtime |
| Registry | approved public/private registry and integrity metadata |
| Versioning | direct dependencies intentionally constrained; transitive overrides documented |
| Audit | blocking Production dependency audit at approved severity |
| Remediation | owner-approved Critical/High SLA and exception expiry |
| License | dependency license inventory and owner review for restricted terms |
| Removal | unused dependencies removed with regression evidence |
| Update | isolated PR, changelog/advisory review, tests and rollback |

A newly published advisory may block an otherwise unchanged documentation PR. The fix is isolated, verified, merged into the central non-Production branch, then dependent gates are revalidated.

## 4. SBOM and provenance

Each release candidate requires:

- machine-readable SBOM for Production dependencies and relevant build tools;
- commit SHA, source branch, lockfile digest and build environment;
- artifact digest and deployment identifier;
- dependency audit result;
- test/evidence bundle identifiers;
- provenance target aligned to SLSA planning, with actual level recorded only when proven;
- retention period and access control for release evidence.

## 5. CI/CD integrity

- workflows use pinned or reviewed action versions;
- minimal token permissions;
- no untrusted fork secret exposure;
- environment separation and explicit Production approval;
- cache keys cannot substitute unverified artifacts;
- generated files are reviewed and reproduced where material;
- failed/skipped required checks block merge;
- temporary diagnostic workflows are removed before merge;
- CI logs and artifacts exclude secrets and unnecessary personal data.

## 6. Secret management

- company-owned Production secrets only;
- separate Local/CI/Preview/Staging/Production credentials;
- no developer personal provider account for Production;
- rotation, revocation, expiry and access evidence;
- secret scanning for current tree and authorized history scope;
- masked logs and safe test values;
- incident process for suspected exposure.

## 7. Build and release gates

A candidate cannot become release-authorized unless:

1. source SHA and branch are known;
2. lockfile is current and clean install succeeds;
3. Production dependency audit passes or formal exception exists;
4. typecheck, required tests, recovery checks and build pass;
5. SBOM and evidence package are generated;
6. Preview/Staging validation succeeds in approved environment;
7. temporary workflows/files are absent;
8. no required check is red, pending or action-required;
9. rollback/forward-fix path is recorded;
10. Production authorization is separate and explicit.

## 8. Current known incident handling pattern

The July 2026 dependency advisory handling establishes the target pattern only:

- detect through blocking audit;
- isolate the dependency fix from planning PRs;
- capture advisory evidence;
- update direct/override and lockfile minimally;
- remove temporary diagnostic automation;
- run the full quality gate;
- do not merge while an external required check is red.

This example is evidence of a process instance, not proof that every supply-chain control is implemented.
