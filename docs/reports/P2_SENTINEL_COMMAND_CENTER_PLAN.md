# P2 — Sentinel Command Center Plan

## الهدف

تحويل صفحة `/admin/command-center` إلى غرفة عمليات آمنة للمالك القيادي لمنصة ORCA، قابلة للاستخدام من الهاتف عند عدم توفر جهاز كمبيوتر.

المنصة تعمل بنموذج:

- اشتراكات SaaS شهرية.
- بيع كامل للنظام لبعض العملاء.
- مزود المنصة هو المسؤول عن التشغيل، الاستمرارية، الحماية، النسخ الاحتياطية، الحوادث، والتنبيهات.

## الفصل المعماري

- `Command Center`: تشغيل وحماية منصة ORCA.
- `Subscription Center`: الاشتراكات والإيرادات والعملاء.
- `Tenant Workspace`: أعمال العميل العقارية وبياناته.

لا يُسمح لـ Tenant Admin بالدخول إلى غرفة عمليات المنصة.

## صلاحيات الوصول

الوصول محصور في:

- `PLATFORM_OWNER`
- أو دور Platform Super Admin معتمد من قاعدة البيانات.

لا يكفي إخفاء الرابط في الواجهة.

الإجراءات الحساسة تتطلب:

- MFA أو Passkey.
- سبب التنفيذ.
- تأكيدًا ثانيًا.
- مدة انتهاء للموافقة.
- سجل تدقيق كامل.

## فريق وكلاء Sentinel

### Sentinel Watcher
مراقبة التطبيق، قاعدة البيانات، Cron، Webhooks، المدفوعات، WhatsApp وZATCA.

الصلاحية: قراءة فقط وإنشاء تنبيه.

### Incident Triage Agent
تحليل الحوادث، تحديد الخدمة المتأثرة، واقتراح السبب والإجراء.

الصلاحية: اقتراح فقط.

### Recovery Agent
تنفيذ Runbooks معتمدة مثل الصيانة أو Rollback.

الصلاحية: يحتاج موافقة المالك.

### Subscription Agent
متابعة التجديد، فشل الدفع، فترة السماح، التعليق وإعادة التفعيل.

الصلاحية: إجراءات محدودة وقابلة للعكس.

### Payment and Webhook Agent
متابعة الأحداث الفاشلة والمكررة وإعادة المحاولة الآمنة.

الصلاحية: وفق Idempotency وRunbook معتمد.

### Communications Agent
إرسال التنبيهات وتحديث حالة الحادثة.

الصلاحية: تلقائية عبر قوالب معتمدة.

## القيود المطلقة

لا يجوز لأي وكيل تنفيذ:

- Shell حر.
- SQL حر.
- Database reset.
- Production seed.
- Schema migration.
- حذف بيانات العملاء.
- تدوير Secrets تلقائيًا.
- تعديل غير قابل للعكس دون موافقة بشرية.

محادثة Sentinel ليست Terminal.

## أوضاع التشغيل

### الوضع الطبيعي
- مراقبة.
- إنشاء حوادث.
- إرسال تنبيهات.
- دون تغييرات تشغيلية.

### الإصلاحات البسيطة
- إعادة محاولة Webhook آمن.
- إعادة تشغيل Job مقاوم للتكرار.
- إعادة إرسال تنبيه.
- تحديث حالة حادثة.

### وضع الصيانة
- تعليق العمليات الجديدة.
- الإبقاء على دخول المالك القيادي.
- حفظ الأحداث الواردة في Queue.
- عرض رسالة صيانة للعملاء.
- انتهاء تلقائي بعد مدة محددة.

### وضع الطوارئ
- إيقاف Cron jobs الحساسة.
- تعليق إرسال المدفوعات أو ZATCA.
- تعليق معالجة Webhooks مع حفظ الأحداث.
- تفعيل Maintenance Mode.
- Rollback إلى آخر Deployment سليم.
- فتح حادثة حرجة.

### الإصلاح العميق
يتطلب:

- موافقة المالك.
- MFA أو Passkey.
- سببًا مكتوبًا.
- عرض الأثر المتوقع.
- خطة Rollback.
- وقت انتهاء للموافقة.

## التحكم من الهاتف

غرفة العمليات يجب أن تعمل كـ PWA قابلة للتثبيت.

التدفق:

1. وصول Push Notification أو تنبيه.
2. فتح رابط الحادثة.
3. التحقق عبر Passkey أو MFA.
4. عرض الخدمة المتأثرة، العملاء المتأثرين، السبب المرجح، توصية الوكيل، الإجراء المقترح، وخطة الرجوع.
5. اختيار موافقة، رفض، صيانة، Rollback، أو تصعيد بشري.

WhatsApp أو البريد يستخدمان للتنبيه فقط، وليس لتنفيذ أوامر حساسة.

## واجهة غرفة العمليات

### بطاقات الحالة
- التطبيق.
- قاعدة البيانات.
- آخر Deployment.
- آخر Heartbeat.
- الحوادث المفتوحة.
- الموافقات المعلقة.
- Cron jobs.
- Webhooks.
- المدفوعات.
- WhatsApp.
- ZATCA.

### إجراءات الطوارئ
- تفعيل الصيانة.
- إيقاف العمليات الحساسة.
- Rollback.
- تعليق Webhooks.
- تعليق Cron.
- فتح حادثة حرجة.

كل إجراء يعرض التأثير، المدة، خطة الرجوع، والتأكيد.

### فريق الوكلاء
يعرض حالة الوكيل، آخر فحص، المهمة الحالية، آخر نتيجة، مستوى الصلاحية، وعدد النجاحات والإخفاقات.

### الحوادث
كل حادثة تحتوي:

- Incident ID
- Severity
- Affected service
- Affected tenants
- Started at
- Current owner
- Agent recommendation
- Approvals
- Actions performed
- Recovery status
- Request ID
- Deployment commit

## ربط الاشتراكات

يعرض مركز المالك القيادي:

- العملاء النشطين.
- الاشتراكات المتأخرة.
- المدفوعات الفاشلة.
- فترة السماح.
- الحسابات المعلقة.
- التجديدات القادمة.
- الإيراد الشهري MRR.
- SLA حسب الخطة.
- العملاء الذين اشتروا النظام كاملًا.
- عقود الدعم والصيانة.

وكيل الاشتراكات يستطيع:

- إرسال تذكير.
- إعادة محاولة التحصيل وفق السياسة.
- فتح تذكرة.
- تطبيق فترة سماح.
- اقتراح التعليق.

لا يجوز حذف بيانات العميل عند التعليق.

## محرك السياسات

| المستوى | مثال | القرار |
|---|---|---|
| قراءة فقط | Health وLogs | تلقائي |
| منخفض وقابل للعكس | Retry آمن | تلقائي وفق Runbook |
| عالي التأثير | صيانة أو Rollback | موافقة المالك |
| غير قابل للعكس | حذف أو Migration | ممنوع آليًا |

## تخزين الحالة

يجب استخدام قاعدة البيانات أو KV لتخزين:

- وضع التشغيل.
- الحوادث.
- الموافقات.
- مهام الوكلاء.
- محاولات الإصلاح.
- Distributed locks.
- Heartbeats.
- آخر Deployment سليم.

يمنع الاعتماد على متغيرات module-level مثل:

```ts
let healingAttempts = 0
```

## دفعات P2

### P2-A — Health and Readiness
- `/api/health/live`
- `/api/health/ready`
- ربط حالة التطبيق وقاعدة البيانات بمركز القيادة.

### P2-B — Operational State
- تخزين وضع Sentinel.
- الحوادث.
- الموافقات.
- Heartbeats.
- إزالة الحالة داخل الذاكرة.

### P2-C — Agent Control Plane
- تسجيل الوكلاء.
- صلاحيات كل وكيل.
- Runbooks.
- Queue للمهام.
- Audit trail.

### P2-D — Mobile Emergency Control
- PWA.
- Push notifications.
- MFA أو Passkey.
- Maintenance Mode.
- Rollback approvals.

### P2-E — Subscription Operations
- التجديد.
- فشل الدفع.
- فترة السماح.
- التعليق الآمن.
- إعادة التفعيل.
- مراقبة الإيرادات وSLA.

### P2-F — Recovery Drills
- تجربة Rollback.
- اختبار تعطل قاعدة البيانات.
- اختبار Webhooks.
- اختبار تكرار Cron.
- اختبار استعادة Backup.
- قياس RTO وRPO.

## معايير القبول

يستطيع المالك القيادي من الهاتف:

1. معرفة حالة التطبيق وقاعدة البيانات.
2. معرفة الخدمات والعملاء المتأثرين.
3. تفعيل وضع الصيانة.
4. إيقاف العمليات الحساسة.
5. اعتماد Rollback.
6. مراجعة توصيات الوكلاء.
7. قبول أو رفض الإجراءات الحساسة.
8. استلام تقرير الاستعادة.
9. مراجعة سجل تدقيق كامل.
10. إدارة حالات الاشتراكات دون حذف بيانات العملاء.

ولا يمتلك أي وكيل صلاحية مفتوحة أو قدرة على تنفيذ أوامر عشوائية أو تغييرات غير قابلة للعكس.
